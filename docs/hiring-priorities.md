# Hiring priorities

New-job setup and saved jobs share one hiring-priority list. Setup requests authenticated analysis of the whole job description and title, with optional manager notes used to clarify scope or rank already-supported capabilities. The model identifies up to five distinct, role-specific capabilities, explains why each matters, and cites an original JD passage. It preserves required/preferred status, alternatives, numerical thresholds, team ownership and seniority. Sparse descriptions can yield fewer priorities or none. Title-only assumptions, incidental preferences and duplicate tool categories must not displace the actual work.

The setup screen no longer uses the browser keyword extractor or copies selected priorities into screening criteria. Recruiters can use the suggested list as-is, or edit, reorder, add or remove items. Additional priorities are explicitly recruiter-sourced. The same `Hiring priorities` label appears in setup, job details, assessments and comparisons.

`hiring_priority_drafts` stores generated results privately by authenticated actor, workspace and normalized input fingerprint. Repeated navigation and retries reuse the result. The existing direct-request ledger prevents concurrent duplicate provider calls; budget reservations and provider telemetry remain enforced. Results are not silently replaced by extraction when AI is unavailable. Users can retry or explicitly save the job for background generation.

Saving a new job attaches its draft and optional edits in the same transaction. The trigger checks membership, draft ownership and the exact title, description and manager-note snapshot. It preserves server-held quotations and writes the established `job_criteria_tasks.priority_suggestions` / `priority_review` records. Candidate assessment and comparison already consume those records. The worker reuses a matching saved list, so criteria-only changes do not generate another list or overwrite recruiter edits. Changed job descriptions invalidate stale suggestions. Existing jobs retain their priorities; rollout does not backfill or charge every job.

Actual manager feedback remains separately identified assessment context. It does not silently rewrite a reviewed shared list. Custom recruiter priorities are never labeled as explicit JD requirements. Ranking does not introduce numeric weights or knockout rules, and proposed assessment changes continue to require recruiter review.

Verification covers authenticated draft caching, cross-workspace and actor access, source preservation, atomic save, edit/reorder persistence, stale input and account-switch handling, retry without duplicate jobs, and browser layout. Isolated staging also runs six actual-model cases: Azure team engineering, manual QA, account retention, warehouse operations, nursing and a sparse software title. The quality gate verifies role-specific capabilities, scope and alternatives, then checks exact setup-to-job persistence. This is a bounded regression corpus, not a claim of universal accuracy.

Deploy through the existing backend-first staging and release workflow. The additive migration is included in `scripts/core-backend.mjs`; the existing public analysis routes host draft generation, so no additional public function is needed.
