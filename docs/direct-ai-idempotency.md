# Direct analysis duplicate prevention

Reliability checklist #4. Both authenticated analysis routes claim a server-computed SHA-256 identity before budget reservation or provider work. Keys include the resolved evidence and feedback model, scoped to the verified workspace and actor. Identical requests from the same actor share a result across tabs/devices and the two API routes. Changed evidence or another actor gets a separate claim. Membership and saved job context are checked again before every replay.

Duplicate callers poll for up to 80 seconds. Successful results are reusable for two minutes. A fifteen-minute processing claim covers bounded provider HTTP retries and validation repair. Direct calls do not retry ambiguous transport failures or HTTP 408/504 responses; they retain the claim and return an actionable recovery reference. Fine-tuned fallback also stops on ambiguous failures. Other known failed responses release the claim for an explicit retry.

Before provider work, the owner must durably mark its live claim. An expired, cleaned or recovered claim cannot start a late provider call. Provider-started claims are never automatically stolen or deleted. Expired results and never-started claims are removed every minute by `blumr-direct-ai-cleanup`. The backend release checks that this schedule is active before deploying handlers. Tables and server RPCs are service-only, with RLS and revoked client grants.

Admin → System health → Interrupted analyses lists stalled claims. Recovery requires a 20–500 character verification note. For started requests, the administrator must verify the original provider request is no longer running using the displayed claim ID (`direct-<claim>-primary-<attempt>` in provider logs), then acknowledge the potential additional charge. Allow retry releases only that stalled claim, records an audit event, and leaves saved recruiter data intact. A recent or completed claim cannot be released, and ordinary users cannot list or recover other requests. Verification notes should contain operational facts, not candidate details.

Run `node --test tests/*.test.js`, `deno test --allow-env tests/*.test.ts`, `psql ... -f tests/direct-idempotency.sql` and the admin browser journey. The release browser workflow additionally runs `tests/direct-idempotency-live.cjs`: two distinct login sessions, both routes, result replay, browser interruption, changed evidence and foreign-workspace denial. Existing fixture cleanup removes synthetic users/documents and cascades their request rows. Twelve concurrent staging claims were also verified to return one owner and eleven processing states.

The feature prevents duplicate direct requests by the same actor. Intentional separate jobs and requests by different teammates remain separate. Resume uploads continue to use stable content identities; guarded database saves and task revisions protect saved candidate data. Production readiness requires the release and live verification checks to pass; it does not establish simultaneous-user capacity, general failure recovery or backup restoration for checklist #8–#10.
